# ADR-0001：pyPython 寄生在 CPython 之上，不替代、不绕过

- 状态：Accepted
- 记录日期：2026-02-14
- 决策依据：用户明确表述「这个解释器不是用来替代 CPython 的，也不是用来绕过 CPython 的。它是一个寄生在 CPython 之上的、纯粹由 Python 代码构成的解释器。」
- 实施情况：已实施
- 关联记录：与 [ADR-0002](0002-语法简化-实现不简化.md) 共同定义本项目的性质

## 背景与证据

项目最初的目标是「用 Python 实现一个解释器」，并且要做到「比 CPython 慢两个数量级以上」。
在讨论性能测量口径时出现过一次分歧：用来对比的基线应当选哪个。

- 曾经的争议点：用 `exec()` 作为基线时，pyPython 只慢约 10 倍（不到两个数量级）；
  而用 `timeit` 预编译代码对象作基线时，能慢到 500 倍以上。
  当时的倾向是「只报 timeit 基线」，因为那个数字好看。
- 用户随后的澄清（见上方「决策依据」）否定了这个倾向：
  pyPython **就是一段跑在 CPython 里的普通 Python 代码**，
  它不是另一个运行时，谈不上「替代」或「绕过」。
  因此两种基线**口径不同但都真实**，不能只挑有利的那个报。

证据位置：

- 性能对比与双基线如实披露：`pypython.py` 的 `main()` 用例 2
- `exec`/`eval` 的使用范围核验：全文件仅 2 处命中，均在 `main()` 的基线段

## 决策

1. **pyPython 是宿主内的解释器**：它由纯 Python 编写，运行在 CPython 进程内，
   不需要、也不试图脱离 CPython。
2. **`exec` / `eval` 只允许出现在性能基线代码中**，不得出现在解释器的执行路径上。
   这条是硬约束：一旦执行路径依赖宿主求值，pyPython 就不成其为解释器了。
3. **性能对比必须同时报出两个基线**：
   - 基线 A（`timeit`，仅执行、不含编译）
   - 基线 B（`exec`，含编译，与 pyPython 同口径）
   并且**必须标注哪一个没达标**。
4. **不得为了让数字好看而调整口径**。可以调整的是采样量（`rounds`），
   且必须同时声明波动范围。

## 备选方案

- **只报基线 A**：曾被倾向采用，因为它能让「慢两个数量级」这条需求显示达标。
  用户澄清宿主关系后否决——这是挑口径而非做测量。
- **改写成真正的独立运行时**（自带对象模型、内存管理，脱离 CPython）：
  从未被考虑为可行方案。需求要求纯 Python、无第三方库，且项目性质是「寄生」，
  自主运行时与这个定位直接冲突。
- **用 C 扩展加速**：与需求「纯 Python」冲突，不予考虑。

## 后果与风险

收益：

- 定位清晰，性能口径有了**可核验的判断标准**——遇到数字争议时，
  回到「是不是寄生关系、两边口径是否对等」就能裁决。
- 「exec 不进入执行路径」这条约束成了可机械检查的规则，
  而不是靠印象判断。

成本与风险：

- **基线 B 长期不达标**（观测 8.7 ~ 10.5 倍，约 1 个数量级），
  且这是结构性的，不是优化能解决的：`exec` 的编译是 C 写的且一次性，
  而 pyPython 每次调用都重做纯 Python 的词法+语法分析。
- 该数字**会随机器负载波动**（实测 508 ~ 1800 微秒），
  因此结论只能看量级，不能当基准引用。这一点已在 `main()` 输出中声明。

## 受影响代码

- `pypython.py` / `main()`：双基线的测量与如实披露逻辑，含未达标声明
- `pypython.py` / 全文件：`exec`/`eval` 的使用范围（仅基线段，2 处）
- `pypython.py` / `evaluate_source()`：唯一的对外入口，纯 Python 实现
- `pypython_ide.py` / `PyPythonScriptBinding._run()`：IDE 侧调用该入口，不经过宿主求值
