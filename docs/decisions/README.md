# 架构决策记录（ADR）

本项目记录**影响较久、以后值得追溯**的决定。局部技巧和一次性修 bug 不进这里，
它们留在代码里的 `#N「问题」{...}` / `#I<n>「问题」{...}` 注释中。

## 编号与状态

- 编号四位递增，不复用。文件位于 `docs/decisions/NNNN-简短名称.md`。
- 状态：`Proposed`（提案）/ `Accepted`（已确认）/ `Superseded`（被取代）/ `Deprecated`（不再适用）。
- 决策改变时**另建新记录**，不改写旧记录的背景与理由；旧记录标 `Superseded` 并与新记录互链。
- 修正链接或事实错误可以保留原编号。

## 与其他记录体系的关系

代码里的问题记录分两套前缀：

- `#N`（`pypython.py`）：解释器侧问题，当前 N=1..30
- `#I<n>`（`pypython_ide.py`）：运行时代理版 IDE 的问题记录，当前 n=1..19
- 源码改造版（`pypython_idle/`）的问题记录以注释形式写在改动的文件里，
  编号沿用 `#I` 体系继续往下排（见 ADR-0004 与 ADR-0005 的"踩到的坑"小节）

这些是**问题记录**，不是决策记录。当某个问题记录背后其实是一个**长期取舍**时，
才升格为 ADR，并在两边互链。

## 一条贯穿多份记录的教训

本项目反复出现同一类缺陷：**同一个概念在两个地方各写一份规则，然后漂移**。
累计已 12 次（见 ADR-0006 末尾的汇总表）；ADR-0007 新增两例（#23、#24），
ADR-0008 又新增四例（#27、#28、#29、#30）。

**它们的共同特征是「不发生异常，只是行为不对」**——赋值成功、不报错、没效果。
因此不能靠"跑起来没报错"判断正确性。可靠做法只有两条：

1. **读源码找出真正的读取点**，不要猜哪个名字"应该"生效
2. **写一个会失败的对照测试**——测不出问题的测试等于没测

## 第二条教训（ADR-0007 补充）

**当一个 API 反复测不出预期时，先怀疑自己的调用姿势。**

ADR-0007 里 `pyparse.is_block_opener()` 连续三种 `set_lo()` 摆法都返回 `False`，
我一度以为是产品缺陷。真实原因是它的 `lo` 语义是"取 `lo` 位置**之前**那条完整语句"。
改用**真实编辑器端到端**（按回车看缩进）之后立刻验证通过。

同一次改动里还有三处"失败"其实是**测试自己写错了**
（构造器少写一个下划线、空输出被当成必须有输出、喂错 offset）。
所以报告失败之前，先确认测试测的是不是你以为的那件事。

## 第三条教训（ADR-0008 补充）

**一个永远绿的测试比没有测试更坏。**

`tests/test_keyword_sync.py` 从第二版起就在核对"8 份关键字表是否同步"，
但它只 `print` 比对结果、**从不返回非 0**。于是在总入口里，
它永远显示 `[OK]`——即使某份表真的少了一个关键字。
本版把它改成逐项 `check()` + 失败时 `exit(1)`，
并顺手补上了"哪些关键字**不该**出现在哪张表里"的反向断言。

同一条教训还适用于用例的**期望值**：ADR-0008 的短路用例第一版写成
"输出里有 `0` 就算过"——那样即使短路完全失效也会通过，等于没测。
改成检查"副作用函数的输出**没有**出现"才真正起作用。

## 第四条教训（ADR-0008 补充）

**"读"可以随便复制，"写"必须落到真对象上。**

本项目的核心手法就是到处 `encode`/`decode` 绕一圈，
而 `PyPyValue.decode()` 会**新建**对象（列表逐元素 `append`）。
于是 `m[0][1]「55」` 拿到的是"第 0 行的副本"，写进去就丢——
**而且不报任何错**（#30）。加任何"写入容器"的语法时，
都要先问一句：我手上这个是真对象，还是某个被复制出来的副本？
